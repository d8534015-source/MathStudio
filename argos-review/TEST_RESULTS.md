## Windows subprocess encoding repair — focused follow-up

Text-mode `subprocess.run(encoding="utf-8")` decoded both pipes inside Windows reader threads, although native libraries can emit locale-encoded diagnostic bytes. `redirect_stdout` only changes Python output and does not isolate fd 1/Win32 STD_OUTPUT_HANDLE. The repair captures raw bytes in setup, runtime generation and staged inspection. JSON is decoded strictly as UTF-8 on the parent thread; invalid bytes or malformed responses fail validation. Diagnostic stderr alone uses replacement decoding, then only the existing sanitized ASCII exception record is retained. No arbitrary native logs are exposed.

The worker duplicates its original stdout pipe for explicit UTF-8 JSON, redirects native fd 1 and Windows STD_OUTPUT_HANDLE to stderr before optional imports, and retains exception exit codes/safe diagnostics. The exact native library that emitted the PC's byte cannot be identified from the supplied traceback; the fix handles native output independently of its producer/codepage.

New real subprocess regressions emit CP936 `0xCE 0xD2` diagnostic bytes on stdout/stderr and, on Windows, through Win32 WriteFile. They exercise both setup directions, assert no reader-thread exception, and preserve exact Chinese strings in valid JSON. Malformed UTF-8/JSON and unsafe diagnostics are rejected; a second-direction malformed response leaves previous models/receipt untouched. Fixtures represent transport, not genuine translation quality.

## Strict UTF-8 worker input repair — reproduced source of surrogate corruption

The latest OWNER report identifies an integrated str of length 16 with utf8=invalid. In the current input_shape implementation, that flag for a built-in str means strict str.encode('utf-8') raised UnicodeEncodeError. For ordinary Python Unicode this identifies surrogate code points, not a list/type mismatch or malformed UTF-8 bytes inside the str. The new diagnostic adds only high-/low-surrogate counts (Unicode category Cs), never characters or numeric code points.

Confirmed a locale-dependent protocol defect: argos_runtime.run_worker serializes ensure_ascii=False JSON as strict UTF-8 bytes; the isolated worker (-I -u) previously read sys.stdin as locale-dependent text. -I ignores PYTHONUTF8/PYTHONIOENCODING environment settings. On a CP936/surrogateescape text wrapper, the exact 9-character Chinese first self-test sentence becomes a 16-character str with five low surrogates. This precisely reproduces the reported length and invalid-UTF8 condition without translation models. ASCII English stays unchanged. Direct tokenizer probes use Unicode literals from Python source and therefore bypass this broken pipe decoding, explaining their success. Windows's actual stdin codec was not independently measured here; the reproduced conversion and the source defect are established locally.

First corrupt stage in the reproduction: worker stdin text decoding, before JSON parsing, Argos or MiniSBD. json.loads accepts those surrogates in a str; MiniSBD returns slices of that same string; SentencePiece's Python/C++ conversion cannot encode the resulting invalid Unicode. Neither archive corruption nor a SentencePiece/dependency-version defect was established.

Narrow repair: read the input pipe as bytes and decode explicitly with strict UTF-8, independent of locale. The request reader has byte/character bounds. After JSON parsing, reject escaped lone surrogates before importing/initializing optional model libraries. No character dropping, replacement encoding, blanket casts, changed tokenizer path or failed-segment skipping. Valid Chinese, punctuation and supplementary Unicode are preserved. The private-file response channel, CPU/offline limits, hashes, existing dependency locks, teacher approval and both-direction model-activation checks are unchanged.
